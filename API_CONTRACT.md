BIKEFLOW – API CONTRACT
Project: Bicycle Service Management System (BSMS)
Business: BikeFlow
Document: API Contract
Version: 1.0
Status: Approved by all three developers

1. Introduction
1.1 Purpose
This document defines the communication rules between the frontend, backend and database components of the BikeFlow system.
The purpose is to ensure that all three developers can work independently while maintaining compatibility during integration.
1.2 Project architecture
The system consists of three main components:
1. Frontend: User interface developed using HTML, CSS and JavaScript.
2. Backend: Application logic and REST API developed using Python and Flask.
3. Database: Data storage and management using SQLite.
The frontend communicates with the backend through HTTP requests. The backend processes requests, validates information and communicates with the database.
1.3 Technologies
Component	Technology
Frontend	HTML, CSS, JavaScript
Backend	Python, Flask
Database	SQLite
API architecture	REST
Data exchange	JSON
API version	v1.0

Base URL during local development:
http://127.0.0.1:5000/api
All API endpoints described in this document use this base URL.

2. Data Structure
2.1 Repair Order
The main entity managed by the system is a repair order.
All three developers must use the exact field names defined below.
Field	Data type	Generated by	Description
id	Integer	Backend/Database	Unique repair order identifier
customer_name	String	Frontend	Customer's full name
customer_phone	String	Frontend	Customer's phone number
bicycle_type	String	Frontend	Type of bicycle
bicycle_brand	String	Frontend	Bicycle manufacturer
problem_description	String	Frontend	Description of the bicycle problem
status	String	Backend	Current repair order status
created_at	DateTime	Backend	Registration date and time

2.2 Required Fields
The following fields must be provided when creating a repair order:
• customer_name
• customer_phone
• bicycle_type
• bicycle_brand
• problem_description
The following fields must be generated automatically:
• id
• status
• created_at
The initial status of every new repair order must be Registered.
The frontend must not generate the repair order ID or initial status.

3. API Endpoints
The API provides four main endpoints for the initial MVP.
3.1 Create a Repair Order
HTTP Method: POST
Endpoint:/api/orders
Purpose: Register a new bicycle repair order.
The frontend sends the customer's information and bicycle details to the backend.
Request headers:
Content-Type: application/json
Request body:
{
  "customer_name": "Anna Kowalska",
  "customer_phone": "123456789",
  "bicycle_type": "Mountain Bike",
  "bicycle_brand": "Trek",
  "problem_description": "Broken rear brake"
}
Successful response:
HTTP Status: 201 Created
{
  "success": true,
  "message": "Repair order created successfully",
  "order": {
    "id": 1,
    "customer_name": "Anna Kowalska",
    "customer_phone": "123456789",
    "bicycle_type": "Mountain Bike",
    "bicycle_brand": "Trek",
    "problem_description": "Broken rear brake",
    "status": "Registered",
    "created_at": "2026-11-07T12:00:00"
  }
}
The backend validates the information, saves the order in the database and returns the created repair order.
3.2 Retrieve All Repair Orders
HTTP Method: GET
Endpoint:/api/orders
Purpose: Retrieve all repair orders stored in the database.
The frontend uses this endpoint to display the repair orders in the dashboard or orders page.
Successful response:
HTTP Status: 200 OK
{
  "success": true,
  "orders": [
    {
      "id": 1,
      "customer_name": "Anna Kowalska",
      "customer_phone": "123456789",
      "bicycle_type": "Mountain Bike",
      "bicycle_brand": "Trek",
      "problem_description": "Broken rear brake",
      "status": "Registered",
      "created_at": "2026-11-07T12:00:00"
    },
    {
      "id": 2,
      "customer_name": "Piotr Nowak",
      "customer_phone": "987654321",
      "bicycle_type": "Road Bike",
      "bicycle_brand": "Giant",
      "problem_description": "Flat rear tire",
      "status": "In Progress",
      "created_at": "2026-11-07T13:00:00"
    }
  ]
}
If there are no repair orders, the backend returns an empty array:
{
  "success": true,
  "orders": []
}
3.3 Retrieve a Specific Repair Order
HTTP Method: GET
Endpoint:/api/orders/<id>
Purpose: Retrieve one repair order using its unique ID.
Example request:
GET /api/orders/1
Successful response:
HTTP Status: 200 OK
{
  "success": true,
  "order": {
    "id": 1,
    "customer_name": "Anna Kowalska",
    "customer_phone": "123456789",
    "bicycle_type": "Mountain Bike",
    "bicycle_brand": "Trek",
    "problem_description": "Broken rear brake",
    "status": "Registered",
    "created_at": "2026-11-07T12:00:00"
  }
}
If the requested repair order does not exist, the backend returns HTTP 404 Not Found.
3.4 Update Repair Order Status
HTTP Method: PATCH
Endpoint:/api/orders/<id>/status
Purpose: Update the status of an existing repair order.
Example request:
PATCH /api/orders/1/status
Request body:
{
  "status": "In Progress"
}
Successful response:
HTTP Status: 200 OK
{
  "success": true,
  "message": "Order status updated successfully",
  "order": {
    "id": 1,
    "status": "In Progress"
  }
}
The backend must validate the new status before updating the database.

4. Repair Order Status Values
The system supports the following six repair order statuses:
Status	Description
Registered	Repair order has been created
Scheduled	Repair appointment has been arranged
In Progress	Bicycle repair has started
Waiting for Parts	Repair is waiting for required parts
Completed	Repair work has been completed
Cancelled	Repair order or appointment has been cancelled

Important: The backend must reject any status value that is not included in this list.
The initial status for every newly created repair order is Registered.

5. Validation Rules
The backend is responsible for validating all information received from the frontend.
The following rules apply:
1. Customer name must not be empty.
2. Customer phone number must not be empty.
3. Bicycle type must not be empty.
4. Bicycle brand must not be empty.
5. Problem description must not be empty.
6. Required fields must contain valid text.
7. Repair order IDs must be unique.
8. Status values must match the six permitted statuses.
9. Invalid or incomplete requests must not be saved in the database.
The frontend may also perform validation to improve the user experience, but backend validation is mandatory.

6. Error Handling
All API errors must follow a consistent JSON response format.
6.1 Validation Error
Example: Customer name is missing.
HTTP Status: 400 Bad Request
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "customer_name": "Customer name is required"
  }
}
6.2 Repair Order Not Found
HTTP Status: 404 Not Found
{
  "success": false,
  "message": "Repair order not found"
}
6.3 Internal Server Error
HTTP Status: 500 Internal Server Error
{
  "success": false,
  "message": "An internal server error occurred"
}
6.4 HTTP Status Codes
Code	Meaning
200	Request successful
201	Repair order successfully created
400	Invalid request or validation error
404	Requested repair order not found
500	Internal server error

The frontend should display appropriate messages based on the response.

7. Database Requirements
The database developer is responsible for creating and maintaining the SQLite database.
7.1 Database File
Database name: bikeflow.db
Main table: repair_orders
7.2 Proposed Table Structure
Column	SQLite Data Type	Constraints
id	INTEGER	PRIMARY KEY AUTOINCREMENT
customer_name	TEXT	NOT NULL
customer_phone	TEXT	NOT NULL
bicycle_type	TEXT	NOT NULL
bicycle_brand	TEXT	NOT NULL
problem_description	TEXT	NOT NULL
status	TEXT	NOT NULL, DEFAULT 'Registered'
created_at	TEXT	NOT NULL

The created_at field will store an ISO 8601 date/time value.
The database should also restrict status values to the six permitted values where practical.
7.3 Required Database Operations
The database must support:
• Inserting a new repair order.
• Retrieving all repair orders.
• Retrieving a repair order by ID.
• Updating the status of a repair order.
The database must preserve saved information after the application is restarted.
7.4 Database Files
Suggested structure:
database/
├── schema.sql
├── db_connection.py
└── bikeflow.db
schema.sql contains the SQL statements for creating the database tables.
db_connection.py contains database connection and setup logic, if this approach is used.
bikeflow.db is the actual SQLite database file.

8. Responsibilities of Each Developer
8.1 Frontend Developer
Responsible for:
• Developing the HTML pages.
• Designing the CSS layout.
• Implementing JavaScript functionality.
• Creating the repair order registration form.
• Displaying all repair orders.
• Displaying individual repair order details.
• Sending POST requests to create repair orders.

• Validating incoming information.

• Setting initial repair order statuses.
• Handling repair order business logic.
• Communicating with the SQLite database.
• Returning consistent JSON responses.
• Handling errors.
• Testing backend functionality.
8.3 Database Developer
Responsible for:
• Setting up the SQLite database.
• Creating the bikeflow.db database file.
• Designing the database schema.
• Creating the repair_orders table.
• Defining primary keys and constraints.
• Setting default values.
• Supporting the required database operations.
• Ensuring data persistence.
• Providing the SQL schema and database setup instructions.
• Coordinating table and column names with the backend developer.
8.4 Shared Responsibilities
All three developers should:
• Follow the agreed API contract.
• Use consistent field names.

• Test the system together.
• Resolve integration problems.
• Keep GitHub updated with their work.

10. Integration Rules
To avoid compatibility problems:
1. All developers must use the field names specified in Section 2.
2. The frontend must communicate with the backend through the agreed API endpoints.
3. The backend must use the database structure agreed upon with the database developer.
4. The backend is responsible for validation and business logic.
5. The database is responsible for storing and retrieving persistent data.
6. The frontend must handle API responses and display appropriate messages.
7. Any proposed changes to the API or database structure must be discussed by all three developers.
8. The backend must be configured to allow frontend requests during local development, including CORS if the frontend runs on a separate origin.

11. Project Scope – MVP
This API contract covers the initial Minimum Viable Product (MVP).
The included functionality is:
• Creating repair orders.
• Automatically generating repair order IDs.
• Saving repair orders in the database.
• Retrieving all repair orders.
• Retrieving individual repair orders.
• Updating repair order statuses.
• Validating required information.
• Maintaining data after application restart.
The following features are outside the scope of this initial API version:
• Appointment scheduling.
• Technician assignment.
• Customer notifications.
• Payment processing.
• Inventory management.
• Advanced analytics.
These features may be considered for future versions.
